OpenFlow 学習メモ

2026-11-14 · ネットワークスペシャリスト試験対策（SDN）

全体像

OpenFlow では、経路を決める役（OpenFlow コントローラー、以下 OFC）と、パケットを転送する役（OpenFlow スイッチ、以下 OFS）が分かれています。
従来の機器は1台の中で両方を行い、OSPF などで各機器が自律分散的に経路を決めていました。

担当持っているもの
コントロールプレーンOFC（OpenFlow コントローラー）トポロジ、ポリシー、学習した MAC など判断の材料。判断ロジックは OFC 上のアプリケーション
データプレーンOFS（OpenFlow スイッチ）フローテーブル。表を引いて、そのとおりに転送するだけ

OFC と OFS は OpenFlow チャネル（TCP 6653、TLS 推奨）でつながります。
フローエントリの構成要素は、マッチフィールド、優先度、カウンタ、インストラクション（アクション）、タイムアウト（idle / hard）、クッキーです。

テーブルミス時の処理の流れ

フローテーブルに一致するエントリがないと、OFS は Packet-In で OFC に問い合わせます。
OFC は Flow-Mod でエントリを登録し、Packet-Out で問い合わせのあったパケット自体も送り出させます。

Packet-Out を送らないと、最初の1個が取り残されます。
2個目以降は登録済みのエントリに一致するので、OFS だけで転送されます。

OF1.3 で Packet-In になるのは、優先度 0・全一致・アクション CONTROLLER のテーブルミスエントリがある場合だけです。
このエントリがないと、一致しないパケットは破棄されます。

Flow-Mod と Packet-Out の違い

Flow-Mod は今後のルールを登録するメッセージ、Packet-Out は目の前のパケット1個を送らせるメッセージです。
どちらも OFC から OFS へ送ります。

Flow-ModPacket-Out
対象これから来るパケット全般今 OFC の手元にあるパケット1個
フローテーブル変わる（追加・変更・削除）変わらない
効果が続く期間エントリが消えるまでその1回だけ
中身マッチ条件、優先度、アクション、タイムアウト送るパケット（または buffer_id）、アクション（出力ポート）

なぜ両方送るのか

Packet-In で問い合わせてきたパケットは、OFS 上で処理が止まっています。

  • Flow-Mod だけ送った場合：ルールは入りますが、止まっている最初の1個は送り出されません。2個目以降は新しいエントリで流れます。
  • Packet-Out だけ送った場合：その1個は届きます。しかしルールが入らないので、次のパケットもまたテーブルミスになり、毎回 Packet-In が発生します。

そのため通常は、Flow-Mod でルールを入れ、Packet-Out で最初の1個を送り出すセットになります。

たとえ話

OFS を荷物の仕分け係、OFC を上司だと考えます。

  1. 仕分け係が、知らない宛先の荷物について上司に「これはどこへ送りますか」と聞く。これが Packet-In。
  2. 上司が「大阪行きは3番レーン」とマニュアルに書き足す。これが Flow-Mod。
  3. 上司が「その荷物は3番レーンに流して」と指示する。これが Packet-Out。

マニュアルに書き足すだけでは、手元の荷物は流れません。
その場で指示するだけでは、次の大阪行きの荷物でもまた質問しに来ます。

Packet-Out だけを使う場面

  • 宛先がまだ分からないとき：Packet-Out で FLOOD させるだけで、ルールは入れません。L2 学習スイッチで最初の ping の行きがこの動きです。
  • OFC がパケットを作って送らせるとき：トポロジ把握用の LLDP や、OFC が代理で返す ARP 応答などです。
  • 破棄するとき：DROP のルールを Flow-Mod で入れるだけで、Packet-Out は送りません。最初の1個もそのまま捨てられます。

試験での見分け方

  • 「フローテーブルを書き換える」「エントリを追加する」「経路を設定する」は Flow-Mod。
  • 「指定したポートからパケットを送出させる」「フローテーブルは変更しない」は Packet-Out。
  • 「OFS が OFC にパケットを送る」は Packet-In。方向が逆なので混同しないこと。

OFC はどう判断するか

OpenFlow のプロトコル自体は、判断の仕方を決めていません。
OFC 上で動くアプリケーションが判断し、その中身は管理者が自由に作れます。
これが「ネットワークをソフトウェアで制御する」という SDN の意味です。

判断のしかた使う情報例
L2 学習Packet-In で届いたパケットの送信元 MAC と受信ポート「H1 は port1 にいる」と覚え、H1 宛てを port1 に出すエントリを入れる
経路計算ネットワーク全体のトポロジ最短経路や空いている経路を計算し、経路上の各 OFS に Flow-Mod を送る
ポリシー管理者が設定したルールACL、QoS、負荷分散、ブラックリスト

トポロジは、OFC が各 OFS に Packet-Out で LLDP を送らせ、隣の OFS から Packet-In で戻ってくることで把握するのが一般的です。

例：サブネットのブラックリストで破棄する

OFC がブラックリストを持ち、一致した通信を OFS で破棄させることができます。
破棄は、アクションなしのエントリを Flow-Mod で入れることで実現します。

  • リアクティブに入れる場合
    1. 未知の通信が来て、OFS が Packet-In を送る
    2. OFC が送信元 IP をブラックリストと照合する
    3. 一致したら priority=300, ip_src=203.0.113.0/24, actions=なし を Flow-Mod で登録する。Packet-Out は送らない
    4. 以降の同じ送信元は、OFS だけで破棄される
  • プロアクティブに入れる場合
    • リストが先に分かっていれば、接続時に優先度の高い DROP エントリをまとめて入れておく。Packet-In が発生しない

注意点は3つです。

  • OF1.3 では IP アドレスをマスク付きでマッチできるので、/24 などのプレフィックスを1エントリにまとめられる
  • OFS のフローテーブル（TCAM）は容量が小さい。巨大なリストは OFC 側に持ち、OFS には集約したものや idle_timeout 付きのものだけを入れる
  • DROP エントリは通常の転送エントリより優先度を高くする。低いと先に転送エントリに一致して通ってしまう

プロアクティブ型とリアクティブ型

違いは、OFS のフローテーブルにエントリを入れるタイミングです。
判断の材料（ポリシーやブラックリスト）は、どちらの型でも OFC が持っています。

プロアクティブ型リアクティブ型
入れるタイミング通信が来る前通信が来てから
きっかけOFC が自分から Flow-Mod（接続時、設定変更時）Packet-In を受けて Flow-Mod
最初のパケット遅延なしPacket-In の往復ぶん遅れる
フローテーブルの容量あらゆる通信を見越すので多く使う必要な分だけで節約できる
OFC の負荷小さいPacket-In が多いと大きい
OFC 停止時入っているエントリで転送を続けられる新しい通信を処理できない
向いているもの基本経路、既知のブラックリスト未知の通信、細かいフロー制御

実際には両方を併用することが多いです。

メッセージ早見表

経路を書き込むのは Flow-Mod です。Packet-In / Flow-Mod / Packet-Out の3つが頻出セットです。

メッセージ方向役割
Hello双方向接続確立の最初。バージョンを交換する
Features Request / ReplyOFC→OFS / OFS→OFCdatapath_id やテーブル数を問い合わせる
Echo Request / Reply双方向OpenFlow チャネルの死活監視
Packet-InOFS→OFCテーブルミスまたはアクション CONTROLLER のとき、パケットを OFC へ送る
Flow-ModOFC→OFSフローエントリの追加・変更・削除（ADD / MODIFY / DELETE）
Packet-OutOFC→OFS指定したパケットを指定ポートから送出させる。フローテーブルは変わらない
Flow-RemovedOFS→OFCタイムアウトや削除でエントリが消えたことを通知する
Port-StatusOFS→OFCポートの追加・削除・リンクダウンを通知する
Multipart（Stats）OFC→OFS / OFS→OFCフローやポートの統計を取得する

試験向けまとめ

  • 従来は各機器が自律分散的に経路を決める。SDN は OFC が全体を見て集中的に決める
  • 利点：全体最適な経路制御、設定の一元管理、ソフトウェアによる柔軟な制御
  • 欠点：OFC が単一障害点になりうる、Packet-In が多いと OFC に負荷がかかる
  • 優先度：条件が細かい方ではなく、優先度の値が大きい方が採用される
  • テーブルミス：OF1.3 はテーブルミスエントリがないと破棄。OF1.0 は OFC へ送っていた
  • タイムアウト：idle_timeout は一致するたびにリセット。hard_timeout は追加からの時間で必ず切れる

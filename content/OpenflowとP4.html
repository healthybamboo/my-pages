OpenFlowとP4VXLANSDNの現在地VPS基盤設計

P4入門：OpenFlowと比べてわかるデータプレーンプログラミング

2026年11月14日

概要：OpenFlowは「表に記入」、P4は「表の様式から設計」

P4は、スイッチがパケットをどう読み、どう処理するかを記述するプログラミング言語です。正式名は Programming Protocol-independent Packet Processors で、2014年にOpenFlowの提唱者でもあるNick McKeownらが論文で提案しました。現在使われているのは2016年に改訂された P4_16 です。

両者の関係は一言で言うとこうなります。

  • OpenFlow：スイッチの中にあるテーブルの「様式」は仕様で決まっている。コントローラーはその様式どおりにエントリを記入するだけ。
  • P4：テーブルの様式そのもの（どのヘッダを読むか、どのフィールドで照合するか、どんな処理をするか）をプログラムで定義する。エントリの記入はコントローラーが行う点は同じ。

つまりP4はOpenFlowの代わりというより、OpenFlowが「固定」として前提にしていた部分をプログラムできるようにしたものです。

OpenFlowのやり方：決まった列しかないフローテーブル

OpenFlowスイッチのフローテーブルは、照合できる列（マッチフィールド）が仕様で決まっています。OpenFlow 1.0では次の12項目でした。

入力ポート / 送信元MAC / 宛先MAC / EtherType / VLAN ID / VLAN優先度 / 送信元IP / 宛先IP / IPプロトコル / IP ToS / 送信元ポート / 宛先ポート

1つのエントリは「マッチ条件・優先度・アクション・カウンタ」でできています。たとえばルーター的なL3転送をさせるなら、テーブルはこうなります。

優先度マッチ条件アクションカウンタ
124EtherType=0x0800, 宛先IP=10.0.1.0/24宛先MAC書換、TTLを1減らす、ポート1へ出力1,532 pkt
116EtherType=0x0800, 宛先IP=10.0.0.0/16宛先MAC書換、TTLを1減らす、ポート2へ出力87 pkt
0（すべてワイルドカード）コントローラーへPacket-In12 pkt

Open vSwitchなら、コントローラーの代わりに手でこう書けます。

ovs-ofctl -O OpenFlow13 add-flow br0 \
  "priority=124,ip,nw_dst=10.0.1.0/24,actions=mod_dl_dst:00:00:00:00:01:01,dec_ttl,output:1"

ポイントは、ip や nw_dst という列名はスイッチが最初から知っているものしか使えないことです。またロンゲストマッチは機能としてはなく、「プレフィックスが長いほど優先度を高くする」という運用で代用します（上の表の124と116）。

限界

  • 新しいプロトコル（VXLAN、GTP、自社独自ヘッダなど）で照合したければ、仕様改訂とハードウェアの対応を待つしかない。実際にマッチフィールドは1.0の12項目から1.3で約40項目まで増え続けた。
  • アクションも仕様で決まったものしか使えない。「パケットに独自の情報を書き込む」ような処理は書けない。
  • ハードウェアによって対応するフィールドやテーブル容量がバラバラで、「同じOpenFlowなのに機種ごとに動きが違う」問題が起きた。

P4のやり方：パイプラインを丸ごと書く

P4のプログラムは、パケットが入ってから出るまでの流れを「パーサー → Ingress → (キュー) → Egress → デパーサー」というブロックに分けて書きます。OpenFlowでは機器側で固定されていた部分のほとんどが、P4では自分で書く部分になります。

キュー管理だけはP4でもチップ側の固定機能です。BMv2のv1modelでは、この前後にチェックサムの検証と再計算を行うブロックも入ります。

書き比べ：同じL3転送をP4で書くと

OpenFlowの例では「nw_dst で照合して mod_dl_dst, dec_ttl, output」を1行で書きました。P4では、そのnw_dstやdec_ttlという部品そのものを自分で定義します。以下はP4公式チュートリアルの basic.p4 をもとにした例です（P4_16、BMv2向けのv1modelアーキテクチャ）。

① ヘッダの形を定義する。OpenFlowではスイッチが最初から知っていたものです。

header ethernet_t {
    bit<48> dstAddr;
    bit<48> srcAddr;
    bit<16> etherType;
}

header ipv4_t {
    bit<4>  version;
    bit<4>  ihl;
    bit<8>  diffserv;
    bit<16> totalLen;
    bit<16> identification;
    bit<3>  flags;
    bit<13> fragOffset;
    bit<8>  ttl;
    bit<8>  protocol;
    bit<16> hdrChecksum;
    bit<32> srcAddr;
    bit<32> dstAddr;
}

② パーサーを書く。「Ethernetを読み、EtherTypeが0x0800なら続けてIPv4を読む」という状態遷移です。

parser MyParser(packet_in packet, out headers hdr,
                inout metadata meta,
                inout standard_metadata_t standard_metadata) {
    state start {
        packet.extract(hdr.ethernet);
        transition select(hdr.ethernet.etherType) {
            0x0800:  parse_ipv4;
            default: accept;
        }
    }
    state parse_ipv4 {
        packet.extract(hdr.ipv4);
        transition accept;
    }
}

③ アクションとテーブルを定義する。ここがOpenFlowのフローテーブルに当たる部分です。

control MyIngress(inout headers hdr, inout metadata meta,
                  inout standard_metadata_t standard_metadata) {

    action drop() {
        mark_to_drop(standard_metadata);
    }

    // OpenFlowの mod_dl_dst + dec_ttl + output を自分で書く
    action ipv4_forward(bit<48> dstAddr, bit<9> port) {
        standard_metadata.egress_spec = port;
        hdr.ethernet.srcAddr = hdr.ethernet.dstAddr;
        hdr.ethernet.dstAddr = dstAddr;
        hdr.ipv4.ttl = hdr.ipv4.ttl - 1;
    }

    // このテーブルは「宛先IP」の1列だけ、照合方式はlpm
    table ipv4_lpm {
        key = { hdr.ipv4.dstAddr: lpm; }
        actions = { ipv4_forward; drop; }
        size = 1024;
        default_action = drop();
    }

    apply {
        if (hdr.ipv4.isValid()) {
            ipv4_lpm.apply();
        }
    }
}

④ デパーサーで組み立て直す。書き換えたヘッダをどの順番で送り出すかも自分で決めます。

control MyDeparser(packet_out packet, in headers hdr) {
    apply {
        packet.emit(hdr.ethernet);
        packet.emit(hdr.ipv4);
    }
}

⑤ エントリを入れる。ここでようやくOpenFlowの add-flow に当たる操作になります。BMv2のCLIだと次のとおりです。

table_add MyIngress.ipv4_lpm MyIngress.ipv4_forward 10.0.1.0/24 => 00:00:00:00:01:01 1
table_add MyIngress.ipv4_lpm MyIngress.ipv4_forward 10.0.0.0/16 => 00:00:00:00:02:02 2

対応関係を表にするとこうなります。

やりたいことOpenFlowP4
どのヘッダを読むか仕様で固定header と parser で定義
照合する列仕様のマッチフィールドから選ぶtable の key で任意のフィールドを指定
照合方式マスク付き一致＋優先度exact / lpm / ternary を列ごとに選ぶ
実行する処理仕様のアクション（output, dec_ttl など）action を自分で書く
テーブルの順番と条件分岐goto_table でつなぐapply ブロックに if で書く
エントリの投入コントローラーが Flow-Modコントローラーが P4Runtime（またはCLI）

テーブルを定義するのはプログラム、中身を入れるのはコントローラー、という役割分担が核心です。

OpenFlowでは書けないこと

P4の本領は、仕様にないプロトコルや処理をスイッチの中に足せることです。代表的な例を3つ挙げます。

例1：独自ヘッダで転送する

公式チュートリアルの basic_tunnel では、EthernetとIPv4の間に独自のトンネルヘッダを挟んで、そのIDで転送先を決めます。OpenFlowにはこのヘッダの列が存在しないので、照合しようがありません。P4なら数十行の追加で済みます。

header myTunnel_t {
    bit<16> proto_id;   // 中身の種類
    bit<16> dst_id;     // 転送先ID
}

// パーサー：EtherType 0x1212 なら独自ヘッダを読む
state start {
    packet.extract(hdr.ethernet);
    transition select(hdr.ethernet.etherType) {
        0x1212:  parse_myTunnel;
        0x0800:  parse_ipv4;
        default: accept;
    }
}

// 独自ヘッダのフィールドをキーにしたテーブル
table myTunnel_exact {
    key = { hdr.myTunnel.dst_id: exact; }
    actions = { myTunnel_forward; drop; }
}

apply {
    if (hdr.myTunnel.isValid()) {
        myTunnel_exact.apply();
    } else if (hdr.ipv4.isValid()) {
        ipv4_lpm.apply();
    }
}

実務でいえば、携帯網のGTP-Uや新しいトンネル方式への対応を、ASICの作り直しなしに入れられるということです。

例2：INT（パケットに経路の状態を書き込む）

In-band Network Telemetry（INT）は、通過するスイッチがそれぞれ「自分のID、キューの深さ、滞留時間」をパケットに追記していく仕組みです。受信側では、そのパケットがどこで何マイクロ秒待たされたかがわかります。ヘッダを新しく足す処理なので、決まったアクションしかないOpenFlowでは実現できません。P4の代表的な応用例です。

例3：スイッチ内で状態を持つ

P4では register（パケットをまたいで値を保持する配列）が使えます。たとえばフローごとのパケット数を数え、しきい値を超えたらその場でドロップする、といった判断をコントローラーに聞かずにデータプレーンだけで行えます。OpenFlowにもカウンタはありますが、コントローラーが読むためのもので、スイッチ自身がその値で判断を変えることはできません。

制御プレーン：P4RuntimeがFlow-Modの後継

コントローラーがエントリを入れるという構造はOpenFlowと同じです。その通信に使うのがP4Runtime（gRPC＋Protocol Buffers）です。

大きな違いは、コントローラーがテーブルの様式を最初から知っているわけではないことです。P4コンパイラはスイッチ用のバイナリと一緒に P4Info というファイルを出力します。そこに「ipv4_lpm というテーブルがあり、キーは hdr.ipv4.dstAddr のlpm、使えるアクションは…」と書かれていて、コントローラーはそれを読んでエントリを組み立てます。

Pythonの p4runtime-shell で先ほどのエントリを入れると、こうなります。

te = table_entry["MyIngress.ipv4_lpm"](action="MyIngress.ipv4_forward")
te.match["hdr.ipv4.dstAddr"] = "10.0.1.0/24"
te.action["dstAddr"] = "00:00:00:00:01:01"
te.action["port"] = "1"
te.insert()

OpenFlowとの対応は次のとおりです。

役割OpenFlowP4
エントリの追加・削除Flow-ModP4Runtimeの Write（TableEntry）
スイッチ→コントローラーへパケットを上げるPacket-InPacketIn（StreamChannel）
コントローラーからパケットを送るPacket-OutPacketOut
テーブルの様式仕様書で固定P4Infoでプログラムごとに定義
データプレーンの入れ替えできないSetForwardingPipelineConfigでプログラムごと差し替え

ONOSのようなコントローラーは、OpenFlowとP4Runtimeの両方を喋れます。

まとめと、手元で試す方法

観点OpenFlowP4
一言で固定のフローテーブルを外から操作するプロトコルデータプレーンの処理自体を書く言語
新プロトコルへの対応仕様改訂＋機器対応待ちプログラムを書き換えて入れ直す
制御プロトコルOpenFlow自身P4Runtime
主な動作環境Open vSwitch、旧世代のOpenFlowスイッチTofino系ASIC、SmartNIC/DPU、BMv2（ソフトウェア）
現在の位置づけ仮想スイッチの内部で現役大手クラウド、通信事業者、研究で使用

ネスペとして押さえること。試験で問われるのはOpenFlow側で、P4はほぼ出ません。ただし、P4と比べるとOpenFlowの前提がはっきりします。

  • フローエントリ＝マッチ条件＋優先度＋アクション＋カウンタ。複数一致したら優先度の高い方。
  • テーブルミスの扱い（Packet-Inでコントローラーへ、またはドロップ）。
  • プロアクティブ型（事前に全部入れる）とリアクティブ型（初受信でPacket-In→Flow-Mod）の違い。
  • リアクティブ型だとコントローラーの負荷と遅延が問題になる。コントローラーの冗長化も論点。
  • テーブル容量には上限があり、エントリの集約やタイムアウト（idle/hard timeout）で管理する。

手元で試す方法。P4もOpenFlowと同じく無料で動かせます。

  1. p4lang/tutorials を取得する。必要なツール一式入りのVMを作る手順もある。
  2. exercises/basic で、本資料のL3転送を自分で埋める（TODOを埋める形式）。
  3. make run でBMv2とMininetが立ち上がり、h1 ping h2 が通れば完成。
  4. 続けて basic_tunnel で独自ヘッダを試す。

OpenFlowの理解を深めるなら、Mininet＋Open vSwitchで ovs-ofctl dump-flows を眺めながらRyuを動かすのが近道です。

よくある疑問

P4の構文はnginxの設定ファイルっぽい？ テーブル定義（key = {...} など）は宣言型で設定ファイル風ですが、全体はC言語の仲間です。header/structはCの構造体（bit<48> のようなビット幅指定の型）、parserは状態遷移、actionとapplyはほぼCの命令型です。ハードウェアで全パケットを決まった時間で処理するため、ループ、ポインタ、動的メモリ、浮動小数点は基本的に使えません。

一般企業でSDNをやるとき、P4は選択肢に入る？ まず入りません。企業のSDNの目的（集中管理、自動化、可視化）は、Cisco ACIやArista CloudVisionなどのベンダー製品、EVPN/VXLAN、SD-WAN、NSXやOVN、Ciliumなどで実現します。P4を使うのは大手クラウド、通信事業者、機器やDPUのベンダー、研究機関です。サーバー側でデータプレーンをプログラムしたい場合は、P4よりLinuxのeBPF/XDPが現実的です。

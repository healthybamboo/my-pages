DHCP まとめ：基本フロー・リレーエージェント・スヌーピング

2026-11-14

概要

DHCP は、IP を持っていない端末に IP アドレス・サブネットマスク・デフォルトゲートウェイ・DNS などを自動で配る仕組みです。最大のポイントは、クライアントは最初 IP もサーバの場所も知らないので、ブロードキャストで叫ぶしかないこと。そしてブロードキャストはルータ（L3）を越えられません。リレーエージェントもスヌーピングも、この性質から生まれた機能です。

登場人物役割使うポート
DHCP クライアントIP をもらう端末（PC、スマホ、IP 電話など）UDP 68
DHCP サーバアドレスプールを持ち、IP を貸し出す（リース）UDP 67
DHCP リレーエージェントクライアントのブロードキャストを受け取り、別セグメントのサーバへユニキャストで中継する L3 機器UDP 67（送受信とも）
DHCP スヌーピング対応スイッチDHCP メッセージを監視・フィルタする L2 スイッチ（中継はしない）—（パケットを覗くだけ）

メッセージの種類は DHCP パケット内の Option 53（DHCP Message Type）で区別されます。IP アドレスの「貸し出し」はリース期間付きで、期限が来る前に更新が必要です。

基本フロー：DORA

IP 取得は DISCOVER → OFFER → REQUEST → ACK の 4 ステップで、頭文字を取って DORA と呼びます。クライアントが送る 2 つ（D と R）は必ずブロードキャストです。

クライアントは全部終わるまで自分の IP を持たないので、送信元はずっと 0.0.0.0 です。

各メッセージの宛先と届く範囲

#メッセージ送信元 IP宛先 IP宛先 MAC届く範囲
①DISCOVER0.0.0.0255.255.255.255ff:ff:ff:ff:ff:ff同じ VLAN の全端末。ルータ／L3 インターフェイスで止まる
②OFFERサーバの IP255.255.255.255 または提示 IPff:ff:ff:ff:ff:ff またはクライアント MACブロードキャストなら VLAN 全体、ユニキャストならその端末だけ
③REQUEST0.0.0.0255.255.255.255ff:ff:ff:ff:ff:ff同じ VLAN の全端末（提示してくれた全サーバに「こちらを選んだ」と伝えるため）
④ACKサーバの IP255.255.255.255 または割当 IPff:ff:ff:ff:ff:ff またはクライアント MACOFFER と同じ
  • OFFER / ACK がブロードキャストになるかは、クライアントが DISCOVER に立てる broadcast フラグで決まります（IP がないとユニキャストを受け取れない実装用）。
  • リレーを経由する場合、サーバはクライアントではなくリレーエージェントの IP（giaddr）宛にユニキャストで返します（次のリレーの節）。
  • 「届く範囲」の境界は物理的なスイッチの台数ではなく VLAN（＝サブネット）。L2 スイッチを何台またいでも同じ VLAN なら届きます。

その他のメッセージとリース更新

DORA 以外に 4 つのメッセージがあり、全部で 8 種類です。番号は Option 53 の値で、パケットキャプチャで見るときに使えます。

値メッセージ方向いつ使うか
1DHCPDISCOVERク→ササーバを探す（ブロードキャスト）
2DHCPOFFERサ→ク「この IP どう？」と提示する
3DHCPREQUESTク→サ提示を受け入れる／リースを更新する
4DHCPDECLINEク→サもらった IP が既に使われていた（ARP で重複を検知）ので辞退
5DHCPACKサ→ク確定。ここで初めて IP を使い始めてよい
6DHCPNAKサ→ク拒否。例：別のサブネットに移動した端末が古い IP を要求した
7DHCPRELEASEク→サIP を返却する（ユニキャスト）。ipconfig /release など
8DHCPINFORMク→サIP は固定で持っていて、DNS などのオプションだけ欲しい

リース更新（T1 / T2）

リースは期限切れを待たず、段階的に更新を試みます。デフォルトは T1 = リース期間の 50%、T2 = 87.5%です。

  1. T1（50%）— RENEWING：貸してくれたサーバに直接ユニキャストで REQUEST。ACK が来ればリース延長。Discover/Offer は不要。
  2. T2（87.5%）— REBINDING：元のサーバが応答しないので、今度はブロードキャストで REQUEST。どのサーバでも応答してよい。
  3. 期限切れ（100%）：IP を手放し、DISCOVER からやり直し。

もう 1 つよく見るのが INIT-REBOOT：PC を再起動したとき、前回の IP を覚えていれば Discover/Offer を飛ばしていきなり「前の IP 使っていい？」と REQUEST をブロードキャストします。別サブネットに移動していたら NAK が返り、DISCOVER からやり直しになります。

DHCP リレーエージェント

結論：リレーは クライアントのブロードキャストが止まる場所、つまりクライアント VLAN のデフォルトゲートウェイになっている L3 インターフェイス（SVI やルータのポート）に設定します。サーバ側でも、端末側の L2 スイッチでもありません。判断基準は「スイッチをまたぐか」ではなく「サブネット（VLAN）をまたぐか」です。

なぜ必要か

DISCOVER はブロードキャストなので、ルータ（L3 インターフェイス）に届いた時点で捨てられます。サーバが別サブネットにいると届きません。そこで、捨てられる地点にいる L3 機器が代わりに受け取り、サーバへユニキャストで転送します。だから設定場所は「ブロードキャストが死ぬ場所」になります。

彩色した 2 箇所だけがリレー設定です。L2 スイッチは何台あっても設定不要で、サーバと同じ VLAN 10 の端末にもリレーは要りません。

ご質問のケースに当てはめると

構成リレー要否設定場所
L3 スイッチ自体が DHCP サーバ。その配下に L2 スイッチと端末。端末 VLAN の SVI（ゲートウェイ）もその L3 スイッチ上不要—。ブロードキャストがそのまま DHCP サーバ機能に届く。配下の L2 スイッチにも何も設定しない
上と同じだが、配下のスイッチが L3 スイッチで、端末 VLAN のゲートウェイがそちらにある必要配下の L3 スイッチの端末側 SVI。helper の宛先は上位 L3 スイッチ（DHCP サーバ機能）の IP
DHCP サーバが別箱で VLAN 10 にいる。端末は同じコア L3 配下の VLAN 20必要コア L3 の SVI 20。同じ箱につながっていても VLAN が違えば必要
DHCP サーバと端末が同じ VLAN不要—

つまり「DHCP サーバとつながっているところ」に置くのではなく、「端末から見て最初の L3 ホップ」に置く、と覚えるのが簡単です。リレーにはそのサブネットの IP を持ったインターフェイスが必要なので、L2 スイッチにはそもそも設定できません。

リレーの中で起きていること（図の VLAN 20 の例）

リレーは「VLAN 20 側の代理人」です。クライアントとサーバが直接話すことはなく、DORA の 4 メッセージがそれぞれリレーで 2 区間に分かれ、計 8 回の送信になります。

リレーがやっているのは次の 2 つだけです。

向き受け取るもの送り出すもの
クライアント → サーバ（①⑤）VLAN 20 に流れたブロードキャスト同じ中身 + giaddr = 10.0.20.1 を、サーバ宛ユニキャストで（②⑥）
サーバ → クライアント（③⑦）自分（giaddr）宛のユニキャスト同じ中身を VLAN 20 側へ（④⑧）。クライアントはまだ IP がないので、通常はブロードキャストか MAC 宛て

サーバから見ると、相手は常にリレー（10.0.20.1）です。ブロードキャストを受けたこともなければ、VLAN 20 を知る必要もありません。giaddr の値だけで「どのプールから配るか」と「どこへ返すか」を決めています。

リレーの先にもう 1 台 L3 機器がある場合

リレーが必要なのは 1 台だけで、途中の L3 機器にリレーは要りません。リレーが送り出した時点で、パケットは「10.0.20.1 から 10.0.10.5 への UDP」という普通のユニキャストです。途中の機器は他の通信と同じようにルーティングするだけで、中身が DHCP だとも意識しません。

  • リレーは IP を持っている？ → 持っています。L3 スイッチは各 VLAN の SVI に IP を持ち、それがその VLAN のデフォルトゲートウェイです。この IP（10.0.20.1）が giaddr になり、サーバへの送信元にもなります。逆にゲートウェイの IP を持たない機器（L2 スイッチ）はリレーになれません。
  • ブロードキャストである必要がないのはなぜ？ → ブロードキャストが必要なのは「クライアントが IP もサーバの場所も知らない」からです。リレーは自分の IP を持ち、サーバの IP（helper-address）も設定で知っているので、最初から宛先を指定して送れます。
  • 途中の L2 スイッチはフレームをそのまま転送するだけで、MAC も IP も書き換えません。何台入っていても図は変わりません。
  • 条件は次の 2 つだけ：A から 10.0.10.5 へルートがあること。サーバから giaddr（10.0.20.0/24）への戻りルートがあること。途中に FW や ACL があれば UDP 67 を通すことも必要です。

giaddr には 2 つの役割があります。サーバがどのプールから配るかの判断材料と、返信先です。このためサーバ側には各クライアント VLAN 用のスコープと、giaddr への戻りルートが必要です。

Option 82（Relay Agent Information）

リレー（またはスヌーピングスイッチ）が「どの機器のどのポートから来たか」を付け加えるオプションです。Circuit ID（ポートや VLAN）と Remote ID（機器識別子）からなり、サーバはこれを見て「このポートにはこの IP」といった制御ができます。サーバが応答を返すとき、リレーが削除してからクライアントへ渡します。

設定例（Cisco IOS）

interface Vlan20
 ip address 10.0.20.1 255.255.255.0
 ip helper-address 10.0.10.5    ! 冗長化するなら 2 行目を追加
  • リレーとサーバの間に FW があるなら UDP 67 を双方向で許可。
  • Cisco の ip helper-address は DHCP 以外（TFTP、DNS、NetBIOS など）の UDP ブロードキャストも既定で転送します。不要なら no ip forward-protocol udp <port> で外します。

DHCP スヌーピング

DHCP スヌーピングは認証・認可ではなく、L2 スイッチが「どのポートから DHCP サーバの応答が来てよいか」を制限するフィルタ機能です。端末が「誰であるか」は確かめません（それは 802.1X の役割）。守る対象は主に次の 2 つです。

  • 不正 DHCP サーバ（Rogue DHCP）：誰かが家庭用ルータを挿した、攻撃者が偽サーバを立てた——という場合、そちらの OFFER が先に届くと端末が偽のゲートウェイ・DNS を掴まされます（中間者攻撃や通信断）。
  • DHCP スターベーション：MAC を偽装した DISCOVER を大量に送り、プールを使い切らせる攻撃。

なぜ「スヌーピング」か：L2 機器が L7 をのぞく

DHCP は UDP 67/68 の上で動くアプリケーション層のプロトコルです。本来 MAC アドレスしか見ない L2 スイッチがその中身まで開けて読むので、教科書的にはレイヤー違反です。セキュリティのために、あえてそうしています。

  • CPU 処理になる：DHCP パケットはハードウェアの高速転送ではなく、スイッチの CPU に上げて検査されます。レート制限は攻撃対策であると同時に、スイッチの CPU を守る意味もあります。
  • 上位層の情報を下位層の判断に使える：DHCP の ACK を読んでバインディング表を作り、L2 での転送可否（DAI、IP Source Guard）に使えるのは、この「のぞき見」のおかげです。
  • 同じ発想の仲間：IGMP スヌーピング（L2 スイッチが L3 のマルチキャスト参加メッセージを読む）、DAI（ARP の中身を読む）、IP Source Guard（L3 ヘッダを読む）。

語源の snoop は、オランダ語の snoepen（こっそりお菓子をつまむ）から来た「こそこそ嗅ぎ回る」という意味です。その層の機器が本来は気にしなくていい上位層の中身を、横からのぞくことを表しています。

仕組み：信頼ポートと非信頼ポート

スヌーピングを有効にすると、その VLAN の全ポートがデフォルトで 非信頼 (untrusted) になります。本物のサーバやリレーがいる方向のポート（通常はアップリンク）だけを 信頼 (trusted) に設定します。

信頼ポート（trusted）非信頼ポート（untrusted）
どこに設定アップリンク、サーバ直結ポート端末がつながるアクセスポート
サーバ側メッセージ（OFFER / ACK / NAK）通す破棄（これで不正サーバを防ぐ）
クライアント側メッセージ（DISCOVER / REQUEST など）通す通す。ただしレート制限、送信元 MAC と chaddr の一致チェックなどがかかる
RELEASE / DECLINE通すバインディングに記録されたポート以外から来たものは破棄（他人の IP を勝手に返却させない）

副産物：DHCP スヌーピングバインディングテーブル

スイッチは ACK を見て、「MAC アドレス・IP アドレス・VLAN・ポート・リース残り時間」の対応表を自動で作ります。この表が、他の L2 セキュリティ機能の土台になります。

  • DAI（Dynamic ARP Inspection）：バインディングと食い違う ARP を破棄 → ARP スプーフィング対策。
  • IP Source Guard：そのポートに割り当てられた IP 以外を送信元にしたパケットを破棄 → IP なりすまし対策。

つまりスヌーピングは「不正サーバを止める」と同時に「正規に IP をもらった端末の台帳を作る」機能です。固定 IP の端末は台帳に載らないので、DAI / IP Source Guard を使うなら静的エントリが必要です。

DAI と IP Source Guard が防ぐ攻撃

どちらもスヌーピングのバインディング表を「正解」として、端末が送ってきたものと照合します。DAI は ARP の中身（この IP はこの MAC）を、IP Source Guard は普通のパケットの送信元 IP（設定により MAC も）を見ます。

機能見るもの防ぐ攻撃防げないもの
DAIuntrusted ポートから来た ARP の送信元 IP と MAC の組ARP スプーフィング（ARP ポイズニング）による中間者攻撃ARP を使わない攻撃。自分の正規 IP での攻撃
IP Source Guarduntrusted ポートから来た IP パケットの送信元 IP（+ MAC）他人の IP を名乗った通信、送信元を偽った DoS、IP ベース ACL のすり抜け自分の正規 IP での攻撃。ARP スプーフィング（ARP は IP パケットではないため、DAI の担当）

固定 IP の端末は表に載らないので、何もしないと両機能で通信を捨てられます。静的エントリ（ARP ACL や ip source binding）の登録が必要です。

どこに設定するかと注意点

  • 設定するのは端末が直接つながるアクセススイッチ。VLAN 単位で有効化します。リレーと違い、L2 スイッチで動きます。
  • アップリンクを trusted にし忘れると、正規の OFFER も捨てられて全員 IP が取れなくなります（定番の障害）。
  • Cisco などではスヌーピングスイッチがデフォルトで Option 82 を挿入します。その上流のリレー／サーバが「giaddr が 0 なのに Option 82 付き」のパケットを破棄し、IP が取れないことがあります。その場合は挿入を止める（no ip dhcp snooping information option）か、上流側で受け入れる設定（ip dhcp relay information trust-all など）にします。
! Cisco IOS の設定例（アクセススイッチ）
ip dhcp snooping
ip dhcp snooping vlan 20
!
interface GigabitEthernet1/0/48   ! アップリンク
 ip dhcp snooping trust
!
interface range GigabitEthernet1/0/1 - 24   ! 端末ポート（untrusted のまま）
 ip dhcp snooping limit rate 15

Q. trusted ポートの先に不正サーバをつながれたら？

防げません。trusted は「このポートから来たサーバ応答は無条件で通す」という設定なので、その先にあるものは一切検査しません。ただし、現実の穴は「サーバ直結ポートの差し替え」よりも次のほうが多いです。

  • trusted は普通、スイッチ間のアップリンクです。その先の別のスイッチでスヌーピングを有効にしていなければ、そこに刺された不正サーバの OFFER はアップリンク経由で入ってきて通ります。対策は全アクセススイッチで有効にすること。
  • さらに絞るなら、trusted ポートやコア側で ACL を掛け、UDP 67 のサーバ応答を「正規サーバ／リレーの IP からのものだけ」に限定できます。
  • サーバ直結ポートの差し替えは、物理的な入室管理や、ポートセキュリティ（接続できる MAC を固定）・802.1X で守る領域です。

Q. DHCP スターベーションは本当に防げる？

スヌーピング単体では完全には防げません。ご指摘のとおり、MAC を偽装されるとすり抜けられます。実際には「1 ポートが食いつぶせるアドレス数に上限をかける」という考え方で、複数の機能を組み合わせます。

対策仕組みどこまで効くか
MAC 一致チェック（ip dhcp snooping verify mac-address）イーサネットの送信元 MAC と DHCP の chaddr が違うものを破棄「送信元 MAC は 1 つのまま chaddr だけ変える」簡易的な攻撃は止まる。両方そろえて偽装されると素通り
レート制限（limit rate）ポートあたりの DHCP パケット数を制限し、超えたらポートを停止大量送信は止まる。ゆっくり送られると時間稼ぎにしかならない
ポートセキュリティ（MAC 数上限）1 ポートで学習できる MAC を N 個までに制限これが本命。MAC をいくら偽装しても、そのポートが取れるのは N 個分だけ
サーバ側の制限（Option 82 単位）対応サーバなら Circuit ID（ポート）ごとにリース数を制限ポートセキュリティと同じ考え方をサーバ側で実現
802.1X認証しないとそもそも VLAN に入れない未認証端末には攻撃自体をさせない

まとめると、スターベーション対策の主役はスヌーピングよりもポートセキュリティの MAC 数上限です。スヌーピングのレート制限と MAC 一致チェックは、その補助という位置づけになります。
